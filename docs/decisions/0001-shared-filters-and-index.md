# ADR 0001: общие фильтры, подписки и иерархический индекс в матчере

Статус: предложено (обсуждено, не реализовано). Относится к Этапам 3–5.

## Контекст

Матчер проверяет каждое объявление против всех активных фильтров линейно.
При росте числа пользователей это упирается в CPU. При этом многие
пользователи подписываются на одно и то же (категория + город).

## Решения

1. **Фильтр неизменяемый и общий.** Создание = найти или создать по хешу
   нормализованных полей. «Изменить» фильтр = отписаться и подписаться
   на другой. Редактирования общей строки нет.
2. **Пользователь связан с фильтром через подписки:**
   `subscriptions(user_id, filter_id)`. Пользователь может только создать
   фильтр (или найти существующий) и подписаться/отписаться.
3. **Кэш матчера — дерево:** категория → город → уточнения (`query`,
   цена). `NULL` на уровне = ветка `*`; при обходе проверяются точное
   значение и `*`, то есть до четырёх корзин на объявление:
   `(c, city)`, `(c, *)`, `(*, city)`, `(*, *)`.
4. **Фильтры без подписчиков** лениво вычищаются из кэша (иначе они
   проверяются на каждом объявлении впустую).

## Последствия

- `filters` теряет `user_id`, появляется `subscriptions`.
- `matches` становится per filter, а не per user: нужно решить, как
  доставлять подписчикам (fan-out в gateway или строки на пользователя)
  и как показывать историю подписавшимся позже.
- REST: `PATCH`/`DELETE /api/v1/filters/:id` заменяются созданием и
  отпиской от подписки.
- Нужны `UNIQUE` по хешу фильтра и `INSERT ... ON CONFLICT` против гонки
  при одновременном создании одинаковых фильтров.
- `filter.changed` превращается в «подписки изменились / фильтр добавлен».
- Тесты на вставку, удаление и обход дерева — table-driven.

## Открытые вопросы

- Что значит `matches.user_id` и как строить историю для поздних
  подписчиков.
- Нормализация условий: регистр и пробелы в `query`, `NULL` против `0`
  в границах цены.
- Сидер для Этапа 5: доля дубликатов и неравномерное распределение
  фильтров по корзинам, иначе замер получится нереалистично красивым.

## План замера (Этап 5)

Сначала замерить плоский перебор, затем индекс по `(category, city)`,
затем общие фильтры; фиксировать N фильтров, долю совпадений и
распределение по корзинам.
